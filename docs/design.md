# Design and consensus boundary

RouteWindow addresses a common integration gap: transit, cloud-maintenance, and public-facility operators publish changes in prose, while downstream systems need a stable machine-readable availability calendar. A deterministic interval engine can compose updates once their meaning is known. The semantic boundary—whether a notice announces full suspension, restoration, or merely a delay, which routes it affects, and its exact UTC window—requires independent judgment against external text.

The deployer fixes an explicit operator repository, route taxonomy, midnight UTC origin, and bounded horizon. The repository and SHA-256 commitment make each candidate notice stable for leader and validators. A digest alone conveys no semantics, so both sides fetch the complete bytes. The leader's output is one `CLOSE`, `RESTORE`, or `NONE` record with a source quote for actionable notices. Validators do not accept schema or quote-presence alone: they re-fetch, re-hash, verify the quote is contiguous, and independently judge action, all affected and omitted routes, both hour endpoints, and whether another conflicting qualifying event exists. Every boolean must be true. Disagreement rolls back the entire write.

Bulletins are sequenced by filenames `001-*.md` through `012-*.md` under `bulletins/` at immutable 40-character Git commits. This prevents a caller from replaying an old notice out of order. The bounded event log records source URL, hash, interpretation, and post-event schedule hash. The calendar uses half-open `[start,end)` hour intervals so adjoining closures merge, a restoration carves a gap, and a route remains independent from other routes. This is a timetable *as published*, not a sensor, telemetry, or proof-of-service oracle.

Trust and limits: repository authors may publish false or contradictory notices; URL restriction only identifies the chosen publisher. Git hosting availability can delay ingestion. Model disagreement can prevent a valid notice from landing; the operator may publish an unambiguous correction as the next issue. There is no deadline or automatic polling. The model is asked to interpret only one unambiguous whole-hour event per notice; ambiguous or multi-event notices map to `NONE` and should be split into separate bulletins. The 12-issue/168-hour bounds keep validation and reads manageable. This project deliberately contains no financial settlement.
